1 · O problema

A página e as funções moram em programas diferentes

Memórias separadas

Uma função só pode ser chamada por código do mesmo programa. O navegador não enxerga o que está dentro do Node.

O navegador não fala MySQL

O driver mysql2 abre uma conexão TCP na porta 3306. JavaScript de página só faz pedidos HTTP.

E a senha?

Tudo o que vai para o navegador é visível no F12. A senha do banco ficaria exposta para qualquer visitante.

2 · A ponte

A solução: um servidor no meio do caminho

1 o clique chama uma função do script.js · 2 o fetch manda um pedido HTTP · 3 a rota certa recebe o pedido · 4 a rota chama a função do repo · 5 o driver fala com o MySQL · 6 a resposta volta em JSON e a página mostra.

2 · A ponte

HTTP: um pedido, uma resposta

pedido (navegador → servidor)
POST /api/pacientes HTTP/1.1
Host: localhost:3000
Content-Type: application/json

{"nome":"Diego Rocha","cpf":"44455566677"}
resposta (servidor → navegador)
HTTP/1.1 201 Created
Content-Type: application/json

{"id":4}

Método + URL

O que fazer e com o quê. POST /api/pacientes = “crie um paciente”.

Corpo (body)

Os dados que acompanham o pedido, em texto JSON. GET e DELETE não levam corpo.

Status

O número que resume o resultado: 2xx deu certo, 4xx o pedido estava errado, 5xx o servidor falhou.

Veja isso ao vivo: no navegador, F12 → aba Rede (Network). Cada linha é um pedido; clique para ver método, status, corpo e resposta.

2 · A ponte

Cada ação da tela vira um pedido diferente

Na telaPedido HTTPFunção do repoSQLResposta
Abrir a páginaGET /api/pacienteslistarPacientes()SELECT200 + array
Botão CadastrarPOST /api/pacientesinserirPaciente()INSERT201 + {id}
Botão Editar telefonePUT /api/pacientes/4atualizarTelefone()UPDATE200 ou 404
Botão ExcluirDELETE /api/pacientes/4excluirPaciente()DELETE200 ou 404

A URL diz “quem”

/api/pacientes é a lista inteira. /api/pacientes/4 é o paciente de id 4.

O método diz “o quê”

A mesma URL com métodos diferentes faz coisas diferentes: GET lê, POST cria, PUT altera, DELETE apaga.

Esse conjunto de rotas é a API do sistema: o “cardápio” que o frontend pode usar. As funções do repo não mudaram em nada.
2 · A ponte

JSON: a língua que os dois lados entendem

Pela rede só passa texto. Então o objeto vira texto para viajar e volta a ser objeto na chegada.

No navegador

Ida: body: JSON.stringify(dados)
Volta: await resposta.json()

No servidor

Ida: app.use(express.json()) preenche req.body
Volta: res.json(dados)

O cabeçalho Content-Type: application/json avisa o outro lado de que o texto é JSON. Sem ele, o express.json() ignora o corpo e req.body fica vazio.

Express

Biblioteca que cuida do HTTP: recebe os pedidos e chama a função que você ligou a cada rota.

listen(3000)

O programa não termina: fica esperando pedidos na porta 3000. Por isso aqui não tem pool.end(). Para parar: Ctrl+C.

express.static

O mesmo servidor entrega a página. Por isso abrimos http://localhost:3000, e não o arquivo com dois cliques.

CRUD · Read

Listar: a página pede, o servidor responde

frontend/script.js · navegador
async function carregarPacientes() {
  const resposta = await fetch('/api/pacientes');
  const pacientes = await resposta.json();

  corpoTabela.innerHTML = '';
  for (const p of pacientes) {
    const linha = corpoTabela.insertRow();
    linha.insertCell().textContent = p.id;
    linha.insertCell().textContent = p.nome;
    linha.insertCell().textContent = p.cpf;
    // ... demais colunas e botões
  }
}

carregarPacientes();  // ao abrir a página
backend/server.js · Node
app.get('/api/pacientes', async (req, res) => {
  const pacientes = await repo.listarPacientes();
  res.json(pacientes);
});




// backend/pacientesRepo.js (parte 1)
async function listarPacientes() {
  const [rows] = await pool.execute(
    'SELECT id, nome, cpf, data_nascimento, telefone ' +
    'FROM pacientes ORDER BY id');
  return rows;
}

fetch(url)

Sem mais nada, faz um GET. É assíncrono como o banco: precisa de await.

app.get(url, função)

“Quando chegar um GET nesta URL, rode esta função.” req = o pedido, res = a resposta.

O array faz a viagem toda

rows do MySQL → res.json → resposta.json() → linhas da tabela.

No projeto, o fetch fica dentro de uma função auxiliar pedir(método, url, dados) para não repetir código. Ela aparece no slide de erros.

CRUD · Create

Cadastrar: os dados do formulário viajam no corpo

frontend/script.js · navegador
form.addEventListener('submit', async (evento) => {
  evento.preventDefault();  // não recarrega a página

  // { nome: '...', cpf: '...', ... }
  const dados = Object.fromEntries(new FormData(form));

  const resposta = await fetch('/api/pacientes', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(dados),
  });
  const { id } = await resposta.json();

  avisar(`Paciente cadastrado com id ${id}`);
  await carregarPacientes();  // atualiza a tabela
});
backend/server.js · Node
app.post('/api/pacientes', async (req, res) => {
  const { nome, cpf, data_nascimento, telefone }
    = req.body ?? {};

  // confere de novo o que a página mandou
  if (!nome || !/^\d{11}$/.test(cpf ?? '')) {
    return res.status(400).json(
      { erro: 'Informe o nome e um CPF com 11 números' });
  }

  const id = await repo.inserirPaciente(
    nome, cpf, data_nascimento || null, telefone || null);

  res.status(201).json({ id });  // 201 = criado
});

preventDefault()

Sem isso, o navegador envia o formulário do jeito antigo e recarrega a página.

req.body

O objeto que a página mandou, já convertido pelo express.json().

Depois de gravar

A tela não muda sozinha: a página pede a lista de novo para mostrar o novo paciente.

CRUD · Update / Delete

Editar e excluir: o id vai na URL

frontend/script.js · navegador
async function editarTelefone(paciente) {
  const telefone = prompt('Novo telefone:');
  if (telefone === null) return;   // cancelou

  await pedir('PUT', `/api/pacientes/${paciente.id}`,
              { telefone });
  await carregarPacientes();
}

async function excluir(paciente) {
  if (!confirm(`Excluir ${paciente.nome}?`)) return;

  await pedir('DELETE', `/api/pacientes/${paciente.id}`);
  await carregarPacientes();
}
backend/server.js · Node
app.put('/api/pacientes/:id', async (req, res) => {
  const { telefone } = req.body ?? {};
  const alterados = await repo.atualizarTelefone(
    req.params.id, telefone || null);

  if (alterados === 0)
    return res.status(404).json(
      { erro: 'Paciente não encontrado' });
  res.json({ mensagem: 'Telefone atualizado' });
});

app.delete('/api/pacientes/:id', async (req, res) => {
  const removidos = await repo.excluirPaciente(
    req.params.id);

  if (removidos === 0)
    return res.status(404).json(
      { erro: 'Paciente não encontrado' });
  res.json({ mensagem: 'Paciente excluído' });
});

:id e req.params

:id é um “buraco” na URL. Pedido para /api/pacientes/4 → req.params.id vale '4'.

affectedRows = 0

Lembra da parte 1? Não é erro do banco: o id não existe. Aqui isso vira o status 404.

Quem é o paciente?

Cada botão da tabela é criado já sabendo o paciente da sua linha. É dele que sai o id da URL.

CRUD · de ponta a ponta

A viagem completa de um clique em “Cadastrar”

Um clique = dois pedidos HTTP: um para gravar e outro para buscar a lista de novo. A página nunca “adivinha” o que está no banco; ela sempre pergunta.
Entre ① e ④ a página fica esperando no await. Enquanto isso o servidor também espera o banco no await dele. São duas esperas encadeadas.
6 · Erros

Quando dá errado: o status conta a história

backend/server.js · no final
// qualquer erro lançado nas rotas cai aqui
app.use((err, req, res, next) => {
  if (err.code === 'ER_DUP_ENTRY') {
    return res.status(409).json(
      { erro: 'Este CPF já está cadastrado' });
  }
  console.error(err);  // detalhe só no terminal
  res.status(500).json({ erro: 'Erro no servidor' });
});
frontend/script.js
async function pedir(metodo, url, dados) {
  const resposta = await fetch(url, {
    method: metodo,
    headers: { 'Content-Type': 'application/json' },
    body: dados ? JSON.stringify(dados) : undefined,
  });
  const corpo = await resposta.json();

  if (!resposta.ok) throw new Error(corpo.erro);
  return corpo;
}
StatusSignificaNo nosso projeto
200 / 201deu certo / criadolistar, editar, excluir / cadastrar
400pedido mal feitofaltou o nome ou o CPF não tem 11 números
404não encontradoid que não existe (affectedRows = 0)
409conflitoCPF repetido: o UNIQUE do banco barrou (ER_DUP_ENTRY)
500erro no servidorbanco desligado, SQL errado, bug no código
Pegadinha do fetch: ele só lança erro se a rede falhar. Um 404 ou 500 chega como resposta normal. Por isso o if (!resposta.ok): sem ele, a página mostraria “sucesso” mesmo com o CPF recusado.
6 · Segurança

O que cada lado pode e não pode saber

A senha do banco nunca sai do servidor

O .env e o db.js ficam na pasta backend/. A página só recebe o que as rotas devolvem. Confira no F12: não há senha em lugar nenhum.

Valide de novo no servidor

O required do HTML ajuda o usuário, mas qualquer pessoa pode mandar um pedido direto, sem passar pela página. A conferência que vale é a do server.js.

Os “?” continuam protegendo

O que vem em req.body e req.params é valor de fora. Ele entra no SQL pelo placeholder, nunca concatenado. SQL injection continua impossível.

textContent, não innerHTML

Se alguém cadastrar o nome <script>…, o innerHTML executaria esse código na tela dos outros. Com textContent, vira só texto.

pedido feito “por fora” da página
$ curl -X POST http://localhost:3000/api/pacientes \
       -H "Content-Type: application/json" -d '{"nome":"Sem CPF","cpf":"123"}'
{"erro":"Informe o nome e um CPF com 11 números"}

Regra geral: o frontend cuida da experiência; o backend cuida das regras; o banco é a última linha de defesa.

Na prática

Rodando na sua máquina

  1. Copie .env.exemplo → .env (os valores padrão já funcionam).
  2. docker compose up -d e espere o (healthy) no docker compose ps. O container roda o schema.sql e o seed.sql sozinho.
  3. cd backend · npm install · node server.js
  4. Abra http://localhost:3000 no navegador.
  5. F12 → aba Rede. Cadastre, edite e exclua, vendo cada pedido passar.
  6. Confira no banco (docker compose exec mysql mysql -ualuno -psenha123 hospital): SELECT * FROM pacientes;
Não abra o index.html com dois cliques. Em file:// não existe servidor para responder a /api/pacientes, e a página mostra “Não foi possível falar com o servidor”.

Fechamento

Checklist da conversa entre frontend e banco

  • A página nunca fala com o banco: ela só faz pedidos HTTP.
  • Cada operação do CRUD tem a sua rota (método + URL).
  • A rota só traduz: lê o pedido, chama o repo, devolve JSON.
  • Dados viajam em JSON nos dois sentidos.
  • O servidor responde com o status certo (201, 400, 404, 409, 500).
  • A página confere resposta.ok e mostra o erro ao usuário.
  • Validação que vale é a do servidor; senha fica no .env.
  • Depois de gravar, a página busca a lista de novo.
O caminho é sempre o mesmo, em qualquer sistema web: tela → fetch → rota → função → SQL → banco, e a resposta volta pelo mesmo caminho.
Exercícios

Agora é com vocês

1 · Busca por nome

Crie a rota GET /api/pacientes/busca?nome=ana usando o buscarPorNome da parte 1 (req.query.nome) e um campo de busca na página.

2 · Editar o nome

3 · Quebre de propósito

4 · Valide o id

Peça DELETE /api/pacientes/abc. Que status volta? Faça a rota responder 400 quando o id não for um número.

5 · Tire o resposta.ok

Comente o if (!resposta.ok) e cadastre um CPF repetido. O que a página diz? Por quê?

6 · Consultas

Crie GET /api/consultas com o JOIN da parte 1 e mostre o resultado em uma segunda tabela.
