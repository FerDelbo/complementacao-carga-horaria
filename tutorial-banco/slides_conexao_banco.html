3 · O banco

Antes do código: a estrutura (schema.sql)

database/schema.sql
CREATE DATABASE IF NOT EXISTS hospital
  CHARACTER SET utf8mb4;   -- acentos e emojis
USE hospital;

CREATE TABLE IF NOT EXISTS pacientes (
  id   INT AUTO_INCREMENT PRIMARY KEY,
  nome VARCHAR(100) NOT NULL,
  cpf  CHAR(11) NOT NULL UNIQUE,
  data_nascimento DATE NULL,
  telefone  VARCHAR(20) NULL,
  criado_em TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_pacientes_nome (nome)
) ENGINE = InnoDB;

CREATE TABLE IF NOT EXISTS consultas (
  id          INT AUTO_INCREMENT PRIMARY KEY,
  paciente_id INT NOT NULL,
  medico      VARCHAR(100) NOT NULL,
  data_hora   DATETIME NOT NULL,
  status ENUM('agendada','realizada','cancelada')
         DEFAULT 'agendada',
  FOREIGN KEY (paciente_id) REFERENCES pacientes(id)
    ON DELETE CASCADE
) ENGINE = InnoDB;

PRIMARY KEY + AUTO_INCREMENT

O banco gera o id. Seu código não inventa ids: ele pergunta qual foi gerado.

NOT NULL / UNIQUE

Regras que o banco garante, mesmo se o código esquecer. Violou? O banco devolve erro.

INDEX

Como o índice de um livro: buscar por nome não precisa ler todas as linhas.

FOREIGN KEY

Toda consulta aponta para um paciente que existe. CASCADE: apagou o paciente, apaga as consultas.

ENGINE = InnoDB

Motor com transações (COMMIT/ROLLBACK) e chaves estrangeiras.

O que acontece em connect(): o handshake

Os passos ①–④ custam várias idas e voltas pela rede. Por isso abrir uma conexão nova para cada query é lento, e é por isso que existe o pool (mais adiante).

4 · Conectar

O ciclo de vida de toda operação

Python — tudo à mão
conn = mysql.connector.connect(**CONFIG)  # 1
cur  = conn.cursor()                      # 2
cur.execute("SELECT nome FROM pacientes") # 3
linhas = cur.fetchall()                   # 4
conn.commit()                             # 5
cur.close(); conn.close()                 # 6
JavaScript — tudo à mão
const conn = await mysql.createConnection(config); // 1
                                                  // 2 (não existe)
const [linhas] = await conn.query(                // 3
  'SELECT nome FROM pacientes');                  // 4
await conn.commit();                              // 5
await conn.end();                                 // 6

No projeto, os passos 1, 5 e 6 ficam escondidos numa função auxiliar para ninguém esquecer. É o próximo slide.

4 · Conectar · Python

db.py: o pool e o “with” que nunca esquece

python/db.py
from mysql.connector import pooling
from contextlib import contextmanager

_pool = None

def get_pool():
    global _pool
    if _pool is None:               # cria só 1 vez
        _pool = pooling.MySQLConnectionPool(
            pool_name="hospital_pool",
            pool_size=5, **CONFIG)
    return _pool

@contextmanager
def conexao():
    conn = get_pool().get_connection()
    try:
        yield conn          # seu código roda aqui
        conn.commit()       # deu certo: grava
    except Exception:
        conn.rollback()     # deu erro: desfaz
        raise
    finally:
        conn.close()        # SEMPRE devolve

Como usar

qualquer função
with conexao() as conn:
    cur = conn.cursor()
    cur.execute("...", (valores,))
# saiu do with: commit/rollback
# e devolução já aconteceram
  • yield pausa a função e entrega a conexão para o bloco with.
  • Quando o bloco termina, a função continua: commit().
  • Se o bloco lançar erro, cai no except: rollback().
  • finally roda nos dois casos. Em pool, close() devolve, não fecha.
4 · Conectar · JavaScript

db.js: o pool e por que tudo tem await

javascript/db.js
const mysql = require('mysql2/promise');

const pool = mysql.createPool({
  ...config,
  connectionLimit: 5,        // máx. 5 abertas
  waitForConnections: true,  // a 6ª espera
  dateStrings: true,
});

// pool.execute() já pega, usa e devolve
// a conexão sozinho. Para transações
// precisamos segurar UMA conexão:
async function emTransacao(trabalho) {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    const r = await trabalho(conn);
    await conn.commit();
    return r;
  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();          // SEMPRE devolve
  }
}
No final do script: pool.end(). Pool aberto mantém o Node vivo e o programa nunca termina.
5 · CRUD · Create

INSERT: gravar e descobrir o id gerado

pacientes_repo.py
def inserir_paciente(nome, cpf, nasc=None, tel=None):
    sql = """INSERT INTO pacientes
             (nome, cpf, data_nascimento, telefone)
             VALUES (%s, %s, %s, %s)"""
    try:
        with conexao() as conn:
            cur = conn.cursor()
            cur.execute(sql, (nome, cpf, nasc, tel))
            return cur.lastrowid
    except mysql.connector.Error as err:
        if err.errno == errorcode.ER_DUP_ENTRY:
            raise ValueError(f"CPF {cpf} já cadastrado")
        raise
pacientesRepo.js
async function inserirPaciente(nome, cpf, nasc = null, tel = null) {
  try {
    const [res] = await pool.execute(
      `INSERT INTO pacientes
       (nome, cpf, data_nascimento, telefone)
       VALUES (?, ?, ?, ?)`,
      [nome, cpf, nasc, tel]
    );
    return res.insertId;
  } catch (err) {
    if (err.code === 'ER_DUP_ENTRY')
      throw new Error(`CPF ${cpf} já cadastrado`);
    throw err;
  }
}

Placeholders

Python usa %s, mysql2 usa ?. Os valores vão numa tupla/array na mesma ordem.

O que volta

Não volta linha nenhuma: volta o id gerado (lastrowid / insertId).

CPF repetido

Quem barra é o UNIQUE do banco. O código só traduz o erro.

        cur = conn.cursor(dictionary=True)

async function buscarPorId(id) {
  const [rows] = await pool.execute(
    'SELECT * FROM pacientes WHERE id = ?',
    [id]
  );
  return rows[0] ?? null;  // objeto ou null
}

fetchone() = 1 linha · fetchall() = todas · fetchmany(n) = de n em n (bom para tabelas gigantes). Sem dictionary=True, o Python devolve tuplas: (1, 'Ana Souza', ...).

    'UPDATE pacientes SET telefone = ? WHERE id = ?',
    [telefone, id]);

Retorno = 1

Achou e alterou. Sucesso.

Retorno = 0

Não é erro! Nenhuma linha bateu com o WHERE (id não existe). Seu código decide o que fazer.

Sem WHERE

SQL injection: o erro mais perigoso

python/demo_sql_injection.py
# ERRADO
sql = f"SELECT nome FROM pacientes WHERE cpf = '{entrada}'"
cur.execute(sql)

# CERTO
cur.execute("SELECT nome FROM pacientes WHERE cpf = %s",
            (entrada,))
saída real
SQL montado na mão:
  SELECT nome FROM pacientes WHERE cpf = '' OR '1'='1'
Resultado -> [('Ana Souza',), ('Bruno Lima',),
              ('Carla Mendes',)]  <-- vazou tudo!

Com placeholder %s:
Resultado -> []  <-- texto tratado como valor
Regra de ouro: nenhum valor vindo de fora (formulário, URL, arquivo) entra na string do SQL. Sempre %s / ?.
6 · Segurança

Por que o placeholder protege: prepared statements

mysql2

pool.execute() faz prepare + execute de verdade no servidor (e reaproveita o preparo). pool.query() escapa os valores no cliente. Os dois são seguros com ?; prefira execute.

mysql-connector

cursor() padrão escapa os valores com segurança. cursor(prepared=True) usa prepare no servidor, igual ao execute do mysql2.

6 · Transações

ACID: as 4 promessas do banco

A · Atomicidade

Tudo ou nada. Se a consulta falhar, o paciente também não é gravado.

C · Consistência

Depois do commit, todas as regras (UNIQUE, FK, NOT NULL) continuam valendo.

I · Isolamento

Outras conexões não veem o que você fez até o commit. Ninguém vê “meio cadastro”.

D · Durabilidade

Depois do commit, os dados estão no disco. Acabou a luz? Continuam lá.

Detalhe que confunde: o mysql-connector (Python) começa com autocommit desligado: sem commit(), o INSERT some quando a conexão fecha. Já o mysql2 (JS) usa autocommit ligado: cada execute() fora de transação já grava sozinho.
Curiosidade vista na saída real: o INSERT que falhou “gastou” um id. O AUTO_INCREMENT não volta no rollback, por isso os ids pulam (4 → 6). Isso é normal.
6 · Robustez

Pool de conexões: reaproveitar em vez de abrir sempre

Sem pool

Cada operação refaz o handshake inteiro. Lento, e 1000 usuários = 1000 conexões no banco.

Com pool

Handshake feito uma vez. Emprestar uma conexão pronta custa quase nada.

Vazamento

Pegar e não devolver: o pool esvazia e todo mundo fica na fila para sempre. Por isso finally.

Bônus

JOIN: o banco junta as tabelas pra você

SQL igual nas duas linguagens
SELECT c.id,
       p.nome AS paciente,   -- vem de pacientes
       c.medico,
       c.data_hora,
       c.status
FROM consultas c
JOIN pacientes p ON p.id = c.paciente_id
ORDER BY c.data_hora;
saída real (node main.js)
┌────┬───────────────┬──────────────┬───────────────────────┬────────────┐
│ id │ paciente      │ medico       │ data_hora             │ status     │
├────┼───────────────┼──────────────┼───────────────────────┼────────────┤
│ 2  │ 'Elisa Prado' │ 'Dra. Marta' │ '2026-11-20 14:30:00' │ 'agendada' │

Faça o trabalho pesado no banco. Buscar todas as consultas, depois buscar cada paciente num laço (o famoso problema “N+1”) faz N idas e voltas pela rede. Um JOIN faz uma só.

Fechamento

Checklist da conexão com o banco

  • Estrutura no schema.sql com PK, NOT NULL, UNIQUE e FK.
  • Usuário próprio da aplicação, com o mínimo de permissões.
  • Credenciais no .env, nunca no código nem no GitHub.
  • Um único módulo db cria o pool e empresta conexões.
  • Todo valor externo entra por %s / ?.
  • Operações que andam juntas ficam numa transação.
  • Conexão sempre devolvida (finally / with).
  • Erros do banco tratados pelo código, não pela mensagem.
